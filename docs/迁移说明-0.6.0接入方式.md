# 0.6.0 接入方式迁移说明（2026-10-03）

本文件记录 0.6.0 为什么删掉了一批文件，以及**读旧文档时要忽略什么**。旧文档保留作历史记录，但其中与宿主安装有关的部分**已经作废**，不要照着做。

## 一句话

本插件现在是**标准 dsh bundle**，接入、安装、依赖、配置、生命周期**全部由官方负责**；仓库内不再维护任何安装器、启动脚本、宿主版本固定或验收链。

## 删除了什么，以及为什么

| 已删除 | 它当年做什么 | 为什么不再需要 |
|---|---|---|
| `installer/`（15 个文件） | Windows 一键安装/启动/回滚/卸载 + 固定 CLI lockfile | 官方 `dsh plugin --profile <name> add <地址>` 与应用内「添加插件」已负责安装与依赖解析 |
| `scripts/build-windows-installer.ps1` | 组装 ZIP 一键包、内容哈希、双构建可复现校验 | 不再发布 ZIP；官方接受 npm 包名 / Git 仓库 / 本地目录 / tarball |
| `versions.json` + `installer/dsh-package*.json` | 把宿主 DSH 版本固定成唯一权威源 | **固定宿主版本本身就是坏主意**：宿主升级后这些 pin 只会变成「装了但起不来」。宿主版本改由 `devDependencies` 记录「本实现被复核过的精确版本」 |
| `maintenance.ps1` + `maintenance/` + `vendor/maintenance/` | 统一维护入口与通用层快照（verify/build/acceptance/doctor/sync-versions） | 官方已负责配置校验、profile 补丁与生命周期；这套门禁维护成本高于收益，且会随宿主升级腐坏 |
| `test/windows-installer.test.ps1`、`test/installer-contract.test.mjs` | 安装事务夹具与安装器契约 | 被删对象的测试 |
| `evidence/example-report.json` | `acceptance` 实机链的示例报告 | 该链已删除 |
| `.github/workflows` 的 windows-installer job | 与 `maintenance.ps1 verify` 同口径的 Windows 门禁 | 同上；CI 现在只跑 `npm test` / `npm run check` / peer 模型检查 |

## 读旧文档时忽略什么

`docs/方案-dsh-turn-cost.md`（97 KB 立项与历次变更记录）与 `docs/漏洞报告-Config启动崩溃-20260824.md` 保留作历史。其中以下内容**已作废**：

- 任何提到 `安装.cmd` / 一键包 ZIP / `versions.json` / `maintenance.ps1` / `acceptance` 实机链 / 启动器（`启动 DSH（含额度）.cmd`）/ 固定 3080 端口 / `profiles\web` 假设的段落；
- 例外：`docs/方案-dsh-turn-cost.md` 里的**计费口径、费率分档、额度归因边界、隐私边界**等设计决策**仍然有效**——那些是插件本身的语义，与接入方式无关。

`docs/漏洞报告-Config启动崩溃-20260824.md` 完全有效：它记录 schema 误用会让 cordis 整树拒载、dsh 起不来，是一条仍然适用的教训（见 `docs/DEVELOPMENT.md` §二）。

## 现在的接入方式

见 `README.md`「安装」一节与 `docs/DEVELOPMENT.md` §四。核心：

```powershell
dsh plugin --profile <profile> add <npm 包名 | github:owner/repo | 本地目录 | tarball>
# 或应用内：侧边栏「插件」页 → 添加插件
```

装完**重启该 profile**（bundle 成员是启动期决定的）。
